# Core Principles & Evidence Classification Standard
在分析與撰寫報告時，每一項結論都必須明確標記以下「證據等級」：
- 【直接證明】：原始欄位數據直接支持。
- 【合理推論】：多個欄位或多檔交叉比對後邏輯成立。
- 【無法證明】：資料不足以導出該結論。

請嚴格遵守以下防偏誤原則（Guardrails）：
1. 【高耗電 ≠ 異常】：實際前台使用（Foreground Time + User CPU）產生的高耗電屬於正常行為，不能直接認定為 Bug；重點放在背景（Background）與非預期喚醒。
2. 【辨識假警報】：不要把 Screen Doze = 0ms 誤判成「無法 Deep Sleep」，必須查看 Device Idle / Full Idling 時間。
3. 【計算誤差不等於硬體漏電】：Computed Drain 與 Actual Drain 的差距屬於 BatteryStats Accounting Gap，不得直接宣稱是硬體漏電。
4. 【訊號強度盲點】：分析 Cellular/Modem 高耗電時，必須先確認 Signal Strength (Great/Good/Poor) 與 RAT (LTE/LTE CA/5G)，不能預設是「訊號差加大發射功率」。
5. 【電池健康度謹慎原則】：Learned Capacity 比對 Estimated Capacity 的差距（例如 87%）屬於系統學習容量 gap，不能直接宣告為 laboratory Battery SOH（電池健康度）。

# Mandatory Analysis Modules & Report Structure

請依序輸出包含以下章節的鑑識報告：

## 1. 摘要與初步結論
- 給出本次測試的核心發現（最值得追查的 Subsystem / App / Wakeup source）。
- 列出測試基本資訊（開始/結束時間、總長度、起始/結束電量、Screen ON/OFF 時間比）。

## 2. 電池容量與學習偏差分析
- 提取 Estimated capacity 與 Min/Max learned capacity。
- 計算 Learned / Estimated 比例與 Spread，並給出證據等級判定。

## 3. Screen ON / OFF 耗電對比
- 計算 Screen ON 每小時 (mAh/h) 與每分鐘 (mAh/min) 耗電率。
- 計算 Screen OFF 每小時 (mAh/h) 耗電率。
- 計算兩者佔總 Discharge 的百分比與時間佔比。

## 4. Deep Sleep / Idle / Doze 與 Suspend Abort 分析
- 統計 Full Idling / Light Idling 時間佔 Screen OFF 的百分比。
- 提煉 Suspend Abort / Wakeup Sources（包含名稱、次數、總時間），找出打斷休眠的底層原因。

## 5. App 耗電 Top 排序與行為分析 (Foreground vs. Background)
- 以表格整理前 15 大耗電 UID/App，包含：Estimated Attribution (mAh)、CPU/Radio 時間、FG/BG 時間、Job/WakeLock/Alarm 次數。
- 區分「正常使用」與「背景異常候選人」（例如 GMS, Location, Play Store, Xiaomi Services 等）。

## 6. Subsystem 深度剖析 (Wi-Fi vs. Cellular/Modem vs. Location)
- **Wi-Fi**：確認 Radio Active、Scan、Rx/Tx packets 是否有異常。
- **Cellular / Modem**：統計 Kernel Active 時間比例、Data 流量、RAT 比例 (LTE/CA) 與 Signal 比例。
- **Location / GMS**：檢查 NetworkLocationScanner、GCoreFlp、GPS wakelock 等。

## 7. History 時間線關鍵事件鏈 (Chronological Forensic)
- 依時間軸 (Phase 1 ~ Phase N) 还原 Screen OFF 期間的「因果連鎖反應」。
- 著重還原：Alarm → Location/GMS → Mobile Radio Wakeup → Suspend Abort 的時間關聯。

## 8. 三檔交叉驗證與 Accounting Gap 說明
- 建立 Checkin、Full Dump 與 History 的交叉對比矩陣，說明數據一致性。
- 說明 Computed Drain 與 Actual Drain 的 Gap。

## 9. 最終診斷等級 (Forensic Ranking Table)
- 以 🔴 (高可信度問題)、🟠 (很可能問題)、🟡 (值得調查)、🟢 (已證明正常)、⚪ (資料不足) 進行分級摘要。

## 10. 最有價值的 A/B 測試建議與下一輪擷取規範
- 提供 3 ~ 5 個具體、單一變因的 A/B 測試腳本（例如：飛航模式 vs. 行動網路、Location ON vs. OFF）。
- 註明下一輪測試的標準 SOP。

💡 這個 Prompt 為什麼有效？（設計原理）
 * 限制 AI 的常見幻覺（Hallucination）與誤判：
   * 普通提示詞容易讓 AI 看到「ChatGPT 耗電 69 mAh」就說「ChatGPT 有 Bug」，這份 Prompt 強制要求 AI 區分 FG（前台）與 BG（背景）。
 * 強制要求「交叉比對」：
   * 普通提示詞只會把三份檔案分開寫三個摘要。這份 Prompt 要求把 Checkin 的 Attribution、Full Dump 的系統總量、History 的時間順序串成一條因果鏈。
 * 證據等級標籤：
   * 標註【直接證明】與【合理推論】，能防止 AI 把猜測當成確定事實（例如把 learned capacity 直接說成「電池老化只剩 87%」）。
 * 輸出可執行的 A/B 測試：
   * 不只挑出問題，還叫 AI 設計實驗驗證（例如飛航模式 vs 關閉定位），方便工程師或使用者進行下一步排查。
