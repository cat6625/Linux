##3. Realtime 與 Uptime 的區別

這份 BatteryStats 裡面經常同時出現：

`realtime`
`uptime`


兩者非常重要。

# 3.1 Realtime

`realtime` 可以理解成：

從統計開始後，實際經過的牆上時間（elapsed real time）。

它通常包含：

CPU 運作
螢幕亮著
螢幕關閉
CPU 進入 suspend / sleep

例如：

Time on battery:
10m 18s 524ms `realtime`


代表從開始統計到目前，實際經過：

10 分 18.524 秒

# 3.2 Uptime

`uptime` 則比較接近：

CPU 沒有進入 suspend 的累積時間。

因此當手機進入深度睡眠 / suspend 時：

`realtime` 繼續增加
`uptime` 基本上不增加

例如：

Time on battery:
10m 18s 524ms `realtime`
8m 55s 739ms `uptime`


代表：

實際經過時間       10m 18.524s
CPU 活躍時間約       8m 55.740s
差值約              1m 22.785s


也就是說，在這段約 10 分鐘的時間裡，約有 1 分 23 秒 不屬於 CPU `uptime`。

# 3.3 為什麼兩者會不同？

因為手機可以處於：

Realtime
│
├── CPU active → 計入 `uptime`
│
└── suspend / sleep → 不計入 `uptime`


所以：

Realtime 比 `uptime` 大是正常現象。

這也是為什麼單看 `uptime` 不能當作「手機運行了多久」。

## 17. Including smearing 的意義

例如：

Uid `u0a1175`:
14.1 mAh

Including smearing:
20.1 mAh

proportional:
5.99 mAh


smearing 可以理解成：

Android 將某些無法精確歸屬給單一 App 的系統耗電，按照比例分攤給相關 App。

因此：

14.1 mAh


是較直接歸因的耗電。

而：

20.1 mAh


是加入分攤後的數字。

調查特定 App 時，建議優先看：

cpu=
radio=
wake=
sensor=


而不是單純看 Including smearing。

## 24. 最終結論

這份 BatteryStats 的核心結論可以濃縮成：

本次約 10 分鐘的測試中，手機處於高使用狀態，螢幕亮了 75.4% 的時間；真正最突出的系統活動是 Cellular Radio，行動網路 subsystem 有 83.2% 的時間處於 kernel active 狀態。

同時：

Wi-Fi、GPS、Bluetooth 幾乎可以排除為主要耗電來源，而且 Cellular 訊號在 99% 的時間都很好，因此弱訊號並不是最合理的解釋。

App 層面：

org.thunderdog.challegram（UID 11175 / `u0a1175`）是目前最值得注意的 App，估算 14.1 mAh，其中 10.8 mAh 來自行動 Radio。com.brave.browser（UID 10274 / `u0a274`）則估算 8.14 mAh，其中 7.65 mAh 來自 Radio。

電池本身：

系統估算容量約 5020 mAh，Learned Capacity 約 4364～4368 mAh，但不能僅憑這份資料判定電池健康度為 87%。

最後：

**Computed drain** = 66.2 mAh 不等於實際掉電 66.2 mAh。因為本次 **actual drain** = 0 mAh。因此目前不能用這份 10 分鐘資料直接判斷實際續航或電池是否異常。

如果目的是找出「為什麼手機耗電快」，下一步最有價值的是做一段更長的 螢幕關閉待機測試，並再次取得 BatteryStats。這樣可以把「正常的螢幕使用耗電」與「真正的待機 Radio / wakelock / background activity」分離開來。
