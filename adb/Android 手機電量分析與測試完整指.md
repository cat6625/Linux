# Android 手機電量分析與測試完整指南

這份指南彙整了從環境準備、零干擾測試流程、數據瘦身擷取到 AI 輔助診斷的標準作業程序（SOP）。

---

## 一、 測試前準備與核心觀念

1. **必須重置統計數據（`--reset`）**
   * **原因**：`batterystats` 是持續累加的紀錄器，預設只有在「充飽電（>90%）並拔線」時才會清空。若未手動重置，前幾天的遊戲、影片耗電紀錄會污染本次測試，導致無法分辨背景偷跑元兇。
2. **不需要充到 100% 才能測**
   * **黃金電量區間（30% ～ 85%）**：只要執行重置指令，當下電量即為起點。避開 **95%～100%**（防掉電快樂表區）與 **20% 以下**（系統自動啟動省電模式限制背景活動），30%～85% 的電壓下降最線性、最能反映真實行為。
   * **例外**：僅在測試「整機從滿電到關機的完整續航力」時才需充至 100%。
3. **決定測試情境（切勿混合測試）**
   * **純待機測試（抓背景毒瘤）**：重置後立刻鎖屏靜置 **2～8 小時**（最適合睡前測）。保持平時習慣的 Wi-Fi/行動網路連線，**不要手動清後台**。正常標準為 8 小時掉電 **2%～5%** 以內。
   * **日常操作測試（抓高負載耗電大戶）**：固定螢幕亮度與環境，執行可重複的固定腳本（如滑社群 15 分鐘＋看影片 15 分鐘）持續 **1～2 小時**。

---

## 二、 零干擾無線 ADB 設定（避免拔插線雜訊）

實體拔插 USB 線會強制喚醒螢幕並產生無關的充電電流與系統事件，建議使用 Android 11+ 原生「無線偵錯」進行無接觸測試（確保手機與電腦連上**同一 Wi-Fi**）：

1. **手機端開啟配對**：
   * 前往 **「設定」＞「開發人員選項」＞「無線偵錯」**。
   * 點擊 **「使用配對碼配對裝置」**，記下畫面顯示的 `IP:配對埠號` 與 `6位數配對碼`。
2. **電腦端終端機連線**：
   ```bash
   # 1. 首次配對（輸入手機上的配對埠號與 6 位數密碼）
   adb pair 192.168.1.xxx:配對埠號

   # 2. 正式連線（注意：需改用無線偵錯主頁面上顯示的「連線埠號」）
   adb connect 192.168.1.xxx:連線埠號
   ```
   *(確認 `adb devices` 顯示裝置後，即可徹底拔除實體傳輸線。)*

> **💡 進階替代技巧（有線模擬拔電）**：若無 Wi-Fi 必須插線測試，可用 `adb shell dumpsys battery unplug` 強制讓手機進入純放電模式；**測試結束後務必執行 `adb shell dumpsys battery reset` 還原**，否則電量顯示會凍結。

## 三、 標準電量測試執行 SOP

1. **重置電量統計並開啟完整喚醒紀錄**：
   ```bash
   adb shell dumpsys batterystats --reset
   adb shell dumpsys batterystats --enable full-wake-history
   ```
2. **進入測試狀態**：
   * 若為純待機測試，直接鎖屏靜置（或遠端執行 `adb shell input keyevent 26` 鎖屏），期間勿觸碰手機。
3. **無聲匯出純文字報告（源頭瘦身）**：
   * 測試時間一到，**不要喚醒手機螢幕**，直接在電腦執行以下指令匯出純文字報告（避免產出數百 MB 的龐大 `bugreport.zip`）：
   ```bash
   # 匯出人類可讀的完整電量摘要（約 100KB～500KB）
   adb shell dumpsys batterystats > battery_summary.txt
   ```

## 四、 精華數據擷取與 AI 診斷工作流

`battery_summary.txt` 上半部包含冗長的逐秒歷史紀錄（Battery History），餵給 AI 前應先過濾以節省額度並提升準確率。

### 1. 僅擷取 4 個核心統計區塊
用文字編輯器打開 `battery_summary.txt`（或解壓縮既有 `bugreport.zip` 內的 `.txt` 檔），搜尋並複製以下 **4 個段落**：

1. **`Statistics since last charge`**：總測試時間、亮屏時間、深度休眠（Deep Doze）比例與總掉電量。
2. **`Estimated power use (mAh)`**：螢幕、網路與各 App（以 UID 顯示）的具體耗電量排名。
3. **`All partial wake locks:`**：螢幕關閉後，在背景偷偷喚醒 CPU 的 App 次數與時長（**抓偷跑頭號指標**）。
4. **`All kernel wake locks:`**：底層硬體驅動（數據機 Modem、藍牙、感測器）的喚醒時間。

### 2. AI 專屬診斷提示詞範本
將擷取的 4 個區塊搭配以下指令貼給 AI（如 Claude 或 ChatGPT）：

> 你是一位資深的 Android 系統效能與功耗分析工程師。以下是我從 `dumpsys batterystats` 擷取的測試區間數據（測試情境為：**[填入：純待機 8 小時 / 日常使用 2 小時]**）。
> 
> 請幫我深入分析這份報告，並依序輸出以下結果：
> 1. **健康度總評**：評估這段時間的掉電速度與深度休眠（Doze）進入比例是否正常。
> 2. **前 3 大耗電元兇**：結合 `Estimated power use` 與 `Wake locks`，點出消耗最多電量或頻繁喚醒系統的具體 App（請幫我把 UID 或套件名稱翻譯成常見的 App 名稱）或硬體模組。
> 3. **異常行為診斷**：檢查是否有不合理的頻繁網路喚醒、感測器卡死或基頻（Modem）搜尋訊號異常。
> 4. **具體改善建議**：針對找出的問題，提供使用者端（設定調整）或開發者端（程式優化）的解決方案。
